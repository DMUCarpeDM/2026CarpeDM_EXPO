## 1. 발견 (Discovery)

### 1.1 문제 정의서 ⭐
**한 문장:** 직장 커뮤니케이션(요청·거절·피드백·보고 등)은 실전에서만 늘지만, **안전하게 반복 연습하고 즉각 객관 피드백을 받을 공간이 없다.**

**근거 축** `[중간]` — 아래는 채워 넣을 골격(정량 근거는 출처 확보 후 기입 ⚠️):
- 롤플레이 훈련은 강사 1:다 구조라 **개인별 피드백 밀도 낮음** + 주관 편차.
- 텍스트 챗봇 연습은 **음성·표정·자세**(실제 커뮤니케이션의 대부분)를 못 잡음.
- 자기 커뮤니케이션은 **관찰이 어려움**(내 표정·말투를 스스로 못 봄) → "거울"이 은유이자 실제 폼팩터.

⚠️ **넣으면 강해지는 근거:** 직장 내 소통 문제 관련 통계/서베이 1~2개(출처 명시). 없으면 "정성 관찰"로만 두고 과장 금지.

### 1.2 경쟁 분석 ○ (심사 배점 직결)
⚠️ **경쟁군 확정 필요.** 표 골격만 제시 — 실제 경쟁사·비교는 조사 후 채울 것(지어내지 말 것).

| 구분 | 예시 후보 | 우리 대비 |
|---|---|---|
| 스피치/발표 코칭 앱 | (조사) | 우리는 **직장 상황 롤플레이 + 자세·표정 멀티모달** |
| 텍스트 롤플레이 챗봇 | (조사) | 우리는 **음성·시각 4축 + 객관 점수(judge 신뢰도 검증)** |
| 기업 교육 서비스 | (조사) | 우리는 **온디바이스·즉시·개인화** |

**차별점 3줄** `[중간]`: ① 4축 멀티모달(응답+음성+표현+자세), ② **judge–human 일치도로 검증된** 점수(단순 LLM 점수 아님), ③ 스마트 미러 + 퇴근 영수증의 체험 완결성.

### 1.3 페르소나 ○ → `character-bibles.md` (6종 존재) `[높음]`
6개 캐릭터가 서로 다른 커뮤니케이션 역량 축을 커버. **이 문서에선 재작성 안 함** — character-bibles.md를 정본으로 참조.
- ⚠️ 6 페르소나 각각이 4-Fit 어느 축을 훈련시키는지 **매핑표**는 아직 없으면 추가 가치 큼(심사 논리 보강).

## 2. 전략 (Strategy)

### 2.1 가치 제안 (Value Proposition) ⭐
> **"거울 앞에서 3분, 실제 직장 대화를 연습하고 — 말·표정·자세까지 점수로 돌려받는다."** `[중간, 초안]`

- 대상 사용자 `[낮음, 추정]`: 취업준비생·신입/저연차 직장인(실전 커뮤니케이션 불안군). ⚠️ **1차 타깃 확정 필요.**
- 핵심 편익: 안전한 반복 + 멀티모달 즉시 피드백 + 검증된 객관성.

### 2.2 목표·지표 ⭐
**North Star Metric(안)** `[중간]`: **"체험 완주 + 결과 수용률"** — 관람객이 역할극→결과→영수증까지 완주하고 "내 피드백이 납득된다"고 응답한 비율.

| 층위 | 지표 | 성공 기준(안) |
|---|---|---|
| 체험 | 데모 완주율 | ⚠️ 목표치 설정 |
| 체험 | 세션당 소요시간 | 2~3분 유지(회전율) `[높음, 데모 제약]` |
| 품질 | **judge–human 일치도** | **Krippendorff α ≥ 0.80 = 보고 가능 / 0.667–0.80 = 잠정** `[높음]` |
| 품질 | STT 성공률 | ⚠️ 목표치(현 실패율 확인) |
| 품질 | EXAONE 정상 응답률 | **fallback ≤ (목표)** — 현재 48~81% `[높음]` → **최우선 개선** |
| 심사 | 대상 5축 매핑 충족 | 심사표 입수 후 확정 ⚠️ |

> **철칙** `[높음]`: **일치도(α) 측정 전에는 judge 점수를 논문·전시·평가 어디에도 보고하지 않는다.** golden set ~30+케이스, bootstrap 신뢰구간, 편향 통제(leniency·halo·비결정성).

⚠️ 제품 비전 1문장 / 포지셔닝 한 줄 — 여유 시 추가(○).

### 3.3 기능 명세서 ⭐
**엔드투엔드 파이프라인** `[높음]`:
`관람객 발화 → STT(faster-whisper) → 액터 LLM(EXAONE) 응답 → [세션 종료] → Judge(4-Fit 채점) → 결과 화면 → (선택) 퇴근 영수증`

프롬프트 구조는 `prompt-scenario-architecture.md`(6-layer, anti-sycophancy, 세션 상태 추적, 대화 품질 평가) 참조. **여기선 재작성 안 함.**

기능별 입력/처리/출력/제약:

| 기능 | 입력 | 처리 | 출력 | 제약 |
|---|---|---|---|---|
| 음성 입력 | 마이크 오디오 | faster-whisper 전사 | 텍스트 | 실패 시 재시도·안내 필요 ⚠️ |
| 롤플레이 응답 | 전사 텍스트 + 페르소나 | EXAONE 대화 | 상대역 발화(음성/텍스트) | **fallback 48~81% → 개선 필수** `[높음]` |
| 의미 매칭 | 발화 | bge-m3 임베딩 | 유사도/근거 | — |

| **4-Fit 채점** | 위 신호 종합 | **Judge LLM 루브릭 채점** | 축별 점수 + rationale | **temperature 고정·n회 반복·근거 강제·α 검증 전 미보고** `[높음]` |

## 4. 설계 (Design)

### 4.1 정보구조도(IA) ⭐
Figma `Carpedm` 파일에 화면 실물 존재 `[높음]`: 컴포넌트 라이브러리 + 1차 시안 **9화면** + 개선 시안 **5화면**(데스크톱 폭 ~1511px). UI는 Claude Design export **standalone HTML**로 키오스크 구동.

**플로우 레벨 IA(안)** `[중간]` — 실제 화면명은 Figma와 대조 필요 ⚠️:
```
대기/어트랙트 화면
  └ 시나리오(페르소나) 선택
      └ 역할극 세션 (음성 대화 루프)
          └ 결과 화면 (4-Fit)
              └ 퇴근 영수증 출력 (선택)
                  └ QR 상세 / 종료·리셋
```

### 4.2 유저 플로우 ⭐ (성공/실패/예외)
- **성공:** 위 IA 정주행.
- **실패·예외** `[높음, 시스템 제약 기반]`:
  - STT 인식 실패 → 재시도 안내 / N회 실패 시 스킵·수동 진행 ⚠️ 정책.
  - **EXAONE fallback**(48~81%) → 대체 응답·재생성·안전 멘트로 세션 끊기지 않게 `[높음]`.
  - 표현/자세 신호 미검출(조도·거리·이탈) → 해당 축 제외 채점 or 안내.
  - 프린터 걸림/용지 소진 → 화면 결과로 대체, QR 안내.

### 4.3 와이어프레임 / 화면설계서 ⭐
⚠️ **Figma 9+5 화면과 Claude Design HTML이 정본이므로 여기서 픽셀 스펙을 재작성하지 않음.** 대신 **요소별 디스크립션(동작·조건·정책)** 을 화면별로 붙이는 표를 권장:

| 화면 | 핵심 요소 | 동작/조건 | 정책 연계 |
|---|---|---|---|
| 대기 | 시작 CTA | 터치/근접 시 진입 | — |
| 선택 | 페르소나 카드 | 선택 시 세션 시작 | 페르소나↔4-Fit 매핑 |
| 세션 | 발화 인디케이터·타이머 | STT 상태·실패 처리 | 2~3분 제한 |
| 결과 | 4-Fit 시각화·결정적 순간 | 채점 완료 후 표시 | **α 검증 전 "참고용" 표기** |
| 영수증 | 출력 버튼·QR | 온디맨드 | 소유·미저장 고지 |

> **알려진 이슈** `[높음]`: standalone HTML이 Pretendard를 CDN에서 로드 → **오프라인 키오스크에서 한글 깨짐.** woff2 로컬 번들 + `@font-face` 경로 수정 필요.

### 4.4 정책 정의서 ⭐ (예외·비즈니스 룰)
`[높음, PIPA 표준]`:
- **음성 = 개인정보.** 부스 입구 **수집·이용 동의 문구** 필수(수집 항목·목적·보관·파기 명시). ⚠️ 문구 확정.
- **발화 텍스트·오디오:** 세션 종료 시 **즉시 파기**(부스 미저장).
- **퇴근 영수증:** 관람객 소유물, 부스 보관 안 함.
- **리포트 보관 기간(신설 필요 ⚠️):** QR 상세 회수용 데이터가 있다면 별도 보관·파기 정책(발화 즉시 파기와 분리 항목).
- STT 실패·신호 미검출·프린터 장애 시 처리 규칙 → §4.2.

## 5. 개발 연계 (Delivery)

### 5.1 인수 기준 (Acceptance Criteria) ⭐
기능별 "완료" 정의 `[중간]` (숫자 목표는 ⚠️ 팀 확정):
- **음성 루프:** 조용한 부스 환경에서 STT 성공률 ≥ (목표) & fallback 시에도 세션 끊김 없음.
- **4-Fit 채점:** 4축 점수 + rationale 출력, 동일 입력 n회 반복 시 분산 (허용범위) 이내, **golden set 대비 α ≥ 0.667(잠정)/0.80(정식)** `[높음]`.
- **결과 화면:** 채점 후 (N초) 내 표시, 오프라인 한글 정상 렌더.
- **영수증:** 한글 정상 출력, (N초) 내 인쇄, 소유·미저장 고지 표기.
- **세션 시간:** 2~3분 완주 가능.

## 6. 품질 (Quality)

### 6.1 QA 시나리오 / 테스트 케이스 ⭐
정상·경계·오류 `[중간]`:
- **정상:** 표준 발화로 완주 → 4-Fit → 영수증.
- **경계:** 아주 짧은/긴 발화, 사투리·잡음, 침묵(무발화), 표정·자세 부분 이탈.
- **오류:** STT 완전 실패, EXAONE fallback 연속 발생, 프린터 걸림, 폰트 미로드(오프라인), 전원/부팅 실패.
- **재현 세션:** 실제 흐름 + 각 실패 케이스 리허설(전시 하드웨어 데모는 **반드시 한 번은 실패한다** — 백업 검증).

### 6.2 Definition of Done ⭐
- 기능이 인수 기준(§5.1) 충족 + 실패 케이스에 **끊김 없이** 대응 + 오프라인에서 한글 정상 + judge 점수는 **α 검증 상태 표기**와 함께만 노출.

## 전시 특칙 (EXPO)

### 데모 시나리오 ⭐ → `engagement-features-plan.md` 안무 반영 `[높음]`
