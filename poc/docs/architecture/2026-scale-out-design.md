## PART Ⅰ — Design Doc (TRD)

### 1. 문제·목표

전시(단일 키오스크)에서 검증된 제품을 **기관 상설 배포**(대학 취업지원센터·기업 온보딩)로 확장할 때 필요한 아키텍처를 정한다. 심사위원의 "확장 계획은?"에 답하는 재료이자, 전시 이후 실제 로드맵의 기술 뼈대.

**목표(Goals)**
1. **다기기·다기관**: 한 기관이 여러 키오스크를, 여러 기관이 각자의 데이터를 운영.
2. **중앙 대시보드**: 기관 관리자가 기기 전반의 사용·완주·점수 추이를 본다.
3. **두 왕관 보석 보존**: (a) 온디바이스 프라이버시(영상·음성이 기기 밖으로 안 나감), (b) 오프라인/전시 안정성(외부 의존 없이 동작).
4. **스키마 진화 가능**: create_all 임시방편을 넘어 무중단 마이그레이션 체계.

**비목표(Non-goals)**
- 클라우드 SaaS 멀티리전·수천 동시 세션(현 단계 과설계). AI를 중앙화(=API 키/사용료 부활 — 원칙 위반)하지 않는다.

### 2. 현행 아키텍처 (baseline, 근거)

- 모노레포: React(Vite) + FastAPI + **SQLite**(`core/config.py: database_url`, `MIRROR_TING_DATABASE_URL`로 오버라이드 가능 — conftest가 실제로 사용).
- **AI 전량 온디바이스/로컬**: STT(Whisper→Vosk), 대화(Ollama EXAONE), 임베딩(bge-m3), 영상(브라우저 MediaPipe). API 키 0.
- **집계만 저장**: 영상 원본 미전송, 브라우저가 계산한 숫자 지표만 서버로(`models.Turn.nonverbal_metrics`).
- 기관 골격 이미 존재하나 미연결: `models.Institution`·`Device`·`AnonymousId`(institution_id FK 슬롯 有).
- 세션 접근은 능력 토큰으로 격리됨(최근 보안팩 — `require_session`).
- **주의(확장 시 부채):** ① 스키마 관리는 `create_all`+시드 + 경량 자동 마이그레이션(`seed/run.py:_migrate_columns` — 모델의 새 nullable 컬럼을 기존 테이블에 `ALTER ADD COLUMN`으로 무손실 추가). 단 **추가만** 가능 — FK 제약·인덱스·타입 변경·데이터 마이그레이션은 불가. ② SQLite 전제 코드 — `sessions.py`의 "SQLite는 naive로 저장" datetime 처리, `main.py` 분석 복구의 "SQLite 동시 쓰기 경합 회피 단일 스레드". → **"PostgreSQL 전환 = URL 교체"는 낙관적. 실제는 아래 마이그레이션 항목 필요.**

### 3. 제안 설계 — Edge-First + 중앙 동기화

각 키오스크(**엣지**)는 지금처럼 전체 스택(FastAPI + 로컬 AI + 로컬 DB)을 자립 실행하고, **익명 집계만** 기관 중앙 서버로 밀어 올린다. 중앙은 AI를 돌리지 않고(원칙 보존) 대시보드용 집계 데이터만 보관.

```
  [기관 A]                                   [중앙(기관 A 테넌트)]
 ┌─ 키오스크1 ─────────────┐                ┌──────────────────────────┐
 │ 브라우저(영상 온디바이스)│                │ FastAPI(집계 수집 API)     │
 │ FastAPI + 로컬 AI        │  ── 집계 push →│ PostgreSQL(테넌트 격리)     │
 │ 로컬 DB(세션·전문·오디오)│  (익명·재시도) │ 기관 관리자 대시보드        │
 └──────────────────────────┘                │  · 사용/완주/점수 분포      │
 ┌─ 키오스크2 ─────────────┐  ── 집계 push →│  · 기기 헬스(heartbeat)     │
 │ (동일 자립 스택)         │                └──────────────────────────┘
 └──────────────────────────┘        ▲ 영상·음성·발화 전문은 절대 올라가지 않음
```

**핵심 성질**
- 영상·음성·발화 전문은 **엣지에 머문다**(미저장 동의면 엣지에서 파기 — 보안팩과 동일 원칙). 중앙엔 점수·집계·기기 상태만.
- 중앙이 죽어도 키오스크는 **오프라인으로 계속 동작**하고, 집계는 큐잉 후 재전송(멱등).
- AI는 엣지에만 → **한계비용 0** 서사 유지(교육기관 상설 도입의 핵심 세일즈 포인트).

### 4. 대안과 트레이드오프

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **A. Edge-first + 집계 동기화** (제안) | 프라이버시·오프라인 둘 다 보존, AI 비용 0 | 엣지마다 AI 하드웨어 필요, 동기화 계층 신설 | **채택** |
| B. 중앙 서버 + 씬 클라이언트 | 기기 하드웨어 저렴, 운영 단순 | 오프라인 붕괴, AI 중앙화=비용/키 부활, 음성 전송 프라이버시 훼손 | 기각(왕관 보석 파괴) |
| C. 엣지 캡처 + 중앙 DB 직결 | 대시보드 실시간 | 중앙 DB 다운 시 키오스크도 저장 불가(가용성 결합) | 부분 기각(오프라인 상실) |

### 5. ADR (Architecture Decision Records)

**ADR-1: 데이터 저장 — 엣지 SQLite 유지 + 중앙 PostgreSQL 신설**
- 맥락: 단일 키오스크는 SQLite로 충분(무설정·안정). 다기기 집계·동시성·백업은 SQLite 부적합.
- 결정: **엣지는 SQLite 유지**, **중앙 집계 저장소만 PostgreSQL**. 엣지→중앙은 집계 push.
- 결과: 엣지 단순성 보존. 중앙에 동시성/백업/대시보드 쿼리. 엣지 DB를 PostgreSQL로 통일하는 건 선택(하드웨어 여유 시)이나 필수 아님.

**ADR-2: AI는 엣지 전용 — 중앙 미탑재**
- 맥락: 온디바이스 AI가 프라이버시·비용·오프라인의 근거.
- 결정: 중앙 서버는 AI(STT/LLM/임베딩)를 **돌리지 않는다**. 전량 엣지.
- 결과: "API 키 0·한계비용 0" 유지. 엣지 하드웨어 사양이 배포 요건이 됨(기관 조달 항목).

**ADR-3: 테넌시 = 행 수준 institution_id (Phase 1은 기존 경량 마이그레이션, Alembic은 Phase 2)**
- 맥락: `Institution`/`Device` 골격 존재하나 세션에 미연결. **저장소에 이미 `_migrate_columns`가 있어** 새 nullable 컬럼을 기존 테이블에 무손실 자동 추가한다(무설정 기동 유지).
- 결정: Phase 1은 `RoleplaySession`에 `institution_id`/`device_id` nullable FK를 추가하고 **`_migrate_columns`에 맡긴다**(Alembic 미도입 — 중복·무설정 훼손 회피). PostgreSQL·FK 제약·인덱스·데이터 마이그레이션이 필요해지는 Phase 2에서 **Alembic 도입**.
- 결과: 다기관 스코프의 기반 확보(보안팩의 세션 격리를 테넌트 축으로 확장). 전시 동작 무변화. Alembic은 제약/인덱스가 실제로 필요한 시점까지 유예(과설계 방지).

### 6. 데이터 모델·API 계약 변화

- **모델:** `RoleplaySession.institution_id`·`device_id` FK 추가(현 nullable 기본 → 단일 테넌트 무영향). `Device`에 등록 토큰·`last_ping_at` 활용(이미 필드 有). 중앙 전용 테이블: `SessionAggregate`(세션당 점수·모드·타임스탬프, **전문/오디오 없음**), `DeviceHeartbeat`.
- **동기화 API(중앙):** `POST /ingest/sessions`(기기 토큰 인증, 집계 배치, 멱등 키=엣지 세션 UUID) · `POST /ingest/heartbeat`. 기기 토큰은 `Device` 프로비저닝 시 발급(보안팩의 능력 토큰 패턴 재사용).
- **대시보드 API(중앙):** 기관 관리자 스코프 조회(사용·완주·점수 분포·코호트). 기존 `/admin`을 기관 스코프 RBAC로 승격.
- **하위 호환:** 엣지의 기존 REST는 불변. 동기화는 **추가 레이어**(엣지 백그라운드 태스크).

### 7. 실패 모드

| 상황 | 설계된 거동 |
|---|---|
| 중앙 다운 | 엣지 정상 동작, 집계 로컬 큐잉 → 복구 시 재전송(멱등 키로 중복 무시) |
| 엣지 오프라인 | 로컬 완결, 이후 동기화 |
| 동기화 부분 실패 | 배치 재시도·백오프. 전송 실패가 체험을 막지 않음 |
| 중앙 DB 마이그레이션 | Alembic 롤백 계획 + 유지보수 창(엣지 무관, 대시보드만 영향) |
| 테넌트 오설정 | institution_id 미스코프 쿼리 차단(테스트로 계약 고정 — 보안팩 IDOR 테스트의 테넌트판) |

### 8. 롤아웃 계획

- **Phase 1 (10월 본전시):** *행동 변화 없음.* **전방 호환 스키마**만 선반영 — `RoleplaySession`에 `institution_id`/`device_id` nullable 컬럼 추가(단일 테넌트=NULL), 기존 `_migrate_columns`가 배포 DB에 자동 적용. Alembic은 Phase 2로 유예. 전시는 지금 구현으로 나가되 이후 마이그레이션 표면이 준다.
- **Phase 2 (전시 후, 파일럿 기관 1곳):** 중앙 집계 서버 + PostgreSQL + 동기화 + 최소 대시보드. 키오스크 2~3대.
- **Phase 3 (다기관):** 테넌트 RBAC·기기 플릿 관리·백업/DR 정식화.

### 9. 미해결 질문(설계자→팀)
1. 엣지 DB를 SQLite로 둘지, 여유 하드웨어면 엣지도 PostgreSQL로 통일할지(운영 균질성 vs 단순성).
2. 동기화 주기: 세션 완료 즉시 push vs 배치(N분) — 대시보드 신선도 vs 네트워크/전력.
3. 기관 데이터 처리 계약(누가 개인정보처리자/수탁자인가) — 법무 검토 필요.
4. 중앙 호스팅: 온프레미스(기관 서버) vs 관리형 — "API 키 0" 서사와의 정합.

## PART Ⅱ — ARB 심사 (G2)

각 위원 독립 심사: 우려 → 질문 → 판정(승인/조건부/반려)+조건.

### 위원 1 — 프린시펄 아키텍트
- **우려:** "PostgreSQL 전환 = URL 교체"라는 기존 서사(qa #7)는 **부채를 감춘다** — naive datetime·단일 쓰기 스레드·create_all은 SQLite 전제. Edge-first는 옳지만, "쉽다"는 톤이 심사장에서 역풍 위험.
- **질문:** 동기화 계층은 신규 분산 시스템이다 — 멱등·순서·중복을 어떻게 테스트로 고정하나? Phase 1의 nullable 컬럼이 정말 무행동인가(인덱스·쿼리 경로 영향)?
- **판정:** **조건부 승인.** 조건: (a) "URL 교체" 표현을 "SQLAlchemy 추상화 위 + 마이그레이션 필요"로 정정, (b) 동기화 멱등 키 계약을 ADR로 명문화.

### 위원 2 — 보안 총괄 (AppSec + DPO)
- **우려:** 지금까지 **네트워크 서버가 없던** 제품에 중앙 수집 서버가 생긴다 = **새 공격 표면**. 방금 닫은 IDOR·테넌트 격리를 중앙에서 다시 뚫을 수 있다(기관 A가 B의 집계 열람). 기관 데이터는 PIPA상 **처리 위탁/DPIA** 대상 가능.
- **질문:** 기기 토큰 탈취 시 위조 집계 주입은? 중앙 대시보드 인가가 institution_id로 강제되는 걸 무엇이 보장하나(테스트)? 집계라도 재식별 위험(소수 표본 기관에서 개인 특정)은?
- **판정:** **조건부 승인.** 조건: (a) `institution_id` 테넌트 격리를 IDOR 테스트와 동급 계약 테스트로, (b) 기기 토큰 회전·폐기 설계, (c) 소표본 집계 마스킹(k-익명성 하한), (d) 기관 배포 전 DPIA·처리위탁계약 — 법률 검토(클로드는 변호사 아님).

### 위원 3 — SRE
- **우려:** Edge-first의 가용성은 좋으나 **관측성 공백** — 기관은 "저 키오스크가 죽었는지"를 알아야 한다. 중앙 DB가 단일 실패점이 되면 대시보드·백업이 위험. 마이그레이션 다운타임.
- **질문:** 기기 heartbeat SLO와 알림 경로는? 중앙 PostgreSQL 백업/복구(RPO/RTO) 목표는? 동기화 큐가 무한 성장하지 않게 하는 상한·드롭 정책은? 엣지 스토리지 가득 참 대응은?
- **판정:** **조건부 승인.** 조건: (a) heartbeat 기반 기기 상태 대시보드 + 오프라인 알림, (b) 중앙 DB 백업·복구 목표 명시, (c) 동기화 큐 상한·백프레셔, (d) Phase 2 이전 로드/장애 spike.

### 의장 종합 판정 — **조건부 승인 (Conditional-Go)**
Edge-first + 집계 동기화는 제품의 두 왕관 보석(프라이버시·오프라인)을 지키는 **아키텍처적으로 올바른 선택**이며 만장일치 방향 승인. 단 **Phase 2 착수 전** 아래를 해소해야 정식 통과:

**필수 조건(Phase 2 게이트)**
1. 정정: "PostgreSQL = URL 교체" → "추상화 + Alembic 마이그레이션". (아키텍트)
2. 테넌트 격리(`institution_id`) 계약 테스트 — IDOR 테스트의 테넌트판. (보안)
3. 동기화 멱등 키·큐 상한·재시도 ADR + spike. (아키텍트·SRE)
4. 기기 토큰 수명주기 + 소표본 집계 마스킹. (보안)
5. heartbeat 관측성 + 중앙 DB 백업/복구 목표. (SRE)
6. DPIA·처리위탁 — 법률 검토. (DPO)

**지금(10월) 할 것 = Phase 1 전방 호환만**
