# Mirror-Ting UX Writing Guide

## 0. 적용 범위와 사용 방법

프론트엔드에서 사용자에게 보여주는 문구를 만들거나 수정할 때 이 문서를 참조한다. 화면의 시각적 기준은 [DESIGN.md](./DESIGN.md), 문구의 기준은 이 문서를 따른다.

- 대상: 제목, 설명, 버튼, 메뉴, 입력 안내, 오류, 로딩, 빈 화면, 알림, 접근성 라벨, AI 기능 안내.
- 새 화면을 구현하기 전에 **실제 동작 → 사용자에게 필요한 정보 → 문구 → 화면 배치** 순서로 확인한다.
- 아래 예시는 작성 기준이다. 예시가 있다고 해당 기능·저장 정책·결제가 구현된 것으로 보지 않는다.
- 현재 메인 히어로 제목과 순환 단어는 사용자가 확정한 문구다. 별도 요청 없이 바꾸지 않는다.
- 이 문서는 토스의 가이드를 Mirror-Ting에 맞게 정리한 프로젝트 기준이다. 토스의 공식 문서나 제휴·검수 인증을 뜻하지 않는다.

### 참고 자료

확인일: 2026-10-18. 원문이 바뀌면 필요한 항목을 다시 확인한다.

- [토스의 8가지 라이팅 원칙들](https://toss.tech/article/8-writing-principles-of-toss): 문구를 판단하는 방향.
- [앱인토스 UI/UX 가이드 — UX 라이팅](https://developers-apps-in-toss.toss.im/design/consumer-ux-guide#ux-라이팅): 말투, 능동형, 경어, 행동 안내 기준.

이하의 서비스 용어, AI 분석 안내, 구현 규칙과 예시는 Mirror-Ting을 위한 적용 규칙이다. 토스 원문의 예시를 그대로 옮기지 않는다.

## 1. 문구를 판단하는 여덟 가지 질문

| 기준 | 구현할 때 확인할 질문 |
|---|---|
| 행동 예측 | 버튼 이름만 읽어도 바로 다음 동작을 알 수 있는가? |
| 군더더기 제거 | 빼도 뜻이 같아지는 단어가 있는가? |
| 반복 제거 | 제목과 본문이 같은 내용을 반복하는가? |
| 핵심 집중 | 지금 결정하거나 행동하는 데 필요한 정보인가? |
| 쉬운 말 | 소리 내어 읽었을 때 자연스러운가? |
| 선택 존중 | 사용자를 재촉하거나 불안하게 만들지 않는가? |
| 보편적인 표현 | 업계 용어나 유행어를 몰라도 이해할 수 있는가? |
| 감정 고려 | 기다림·실수·실패 상황에서 사용자를 탓하지 않는가? |

짧게 만드는 것보다 정확하게 전달하는 것이 먼저다. 기능 제한, 비용, 데이터 처리, 분석 한계를 숨기면서 문구를 줄이지 않는다.

## 2. 말투와 문장

### 기본 말투

- 안내와 설명은 해요체로 쓴다. `살펴봐요`, `선택할 수 있어요`처럼 일상적인 말로 안내한다.
- 버튼과 메뉴는 행동이나 목적을 짧게 쓴다. `상황 적기`, `다시 시도하기`, `연습 기록`은 문장형으로 늘이지 않는다.
- 누가 무엇을 하는지 드러낸다. `AI가 대화 상대가 돼요`처럼 주체를 밝힌다.
- 한 문장에는 한 가지 메시지를 담는다. 본문은 필요한 경우에만 덧붙인다.
- 과도한 높임말과 명사 나열을 줄인다. 단, 자연스러운 `적어주세요`, `확인해주세요`까지 기계적으로 없애지 않는다.
- 해결 방법은 가능한 행동으로 안내한다. 실패·제한 사실 자체를 긍정적인 말로 감추지 않는다.

| 피할 표현 | 권장 표현 |
|---|---|
| 시나리오 생성을 진행합니다 | AI가 연습할 대화를 만들어요 |
| 입력이 완료되었습니다 | 입력했어요 — 별도 확인이 필요할 때만 사용 |
| 상황을 입력하시겠어요? | 연습할 상황을 적어보세요 |
| 분석 결과 확인 | 피드백 보기 |
| 사용 불가 | 지금은 사용할 수 없어요. 확인된 이유와 다음 행동을 함께 안내 |
| 무조건 실력이 늘어요 | 대화를 돌아보고 다시 연습할 수 있어요 |

### 문장 부호와 길이

- 설명 문장에는 마침표를 쓴다. 제목·버튼·메뉴에는 불필요한 마침표를 넣지 않는다.
- 느낌표, 말줄임표, 이모지로 관심이나 긴급함을 과장하지 않는다.
- 말투를 맞추려고 의미 없는 감탄·격려를 추가하지 않는다.
- 길이를 맞추려고 핵심 정보를 생략하거나 작은 글씨로 숨기지 않는다.
- 모바일에서 의미 단위로 읽히는지 확인한다. 줄 수를 맞추려고 문구에 공백이나 강제 줄바꿈을 반복해서 넣지 않는다.

## 3. 서비스 용어

| 개념 | 사용자에게 보여줄 표현 | 사용 기준 |
|---|---|---|
| 입력 프롬프트 | 연습할 상황 | 개발 용어 `프롬프트`는 일반 안내에서 풀어 쓴다 |
| 서비스 모드 | 연습 종류 | 선택지는 `면접`, `직장대화`로 통일한다 |
| 페르소나 | 대화 상대 / AI 면접관 | 사용자가 알아야 할 역할을 말한다 |
| 시나리오 | 연습할 대화 / 상황 | 배경 자체를 뜻할 때는 `상황`을 쓴다 |
| Response-Fit | 답변 | 질문과 답변 내용에 관한 설명 |
| Voice-Fit | 목소리 | 속도·크기·멈춤에 관한 설명 |
| Expression-Fit | 표정 | 관찰한 표정 변화에 관한 설명 |
| Posture-Fit | 자세 | 몸의 기울어짐·움직임에 관한 설명 |
| 통합 분석 | 4-Fit 피드백 | 제품 이름은 유지하고 설명은 쉬운 말로 쓴다 |
| 결과 이력 | 연습 기록 | 내비게이션과 연결 화면에서 일치시킨다 |
| 기능 설명 화면 | 사용 방법 | 띄어쓰기를 통일한다 |

코드 식별자·API 필드·모델 이름까지 이 표에 맞춰 변경하지 않는다. UI 문구와 기술 식별자를 구분한다.

## 4. 화면 요소별 작성 규칙

### 제목과 설명

제목은 사용자가 할 일이나 확인할 내용을 말한다. 설명은 제목에 없는 정보만 보탠다.

- 서비스 소개: `연습할 상황을 적으면, AI가 대화 상대가 돼요`
- 4-Fit 소개: `말과 목소리, 표정과 자세를 살펴봐요`
- 입력 영역: `어떤 대화를 연습하고 싶나요?`
- 기능 설명을 위해 추상적인 성장·변화·미래 표현만 나열하지 않는다.

### 버튼과 링크

동작을 확인한 뒤 이름을 정한다. 같은 기능에는 같은 이름을 쓴다.

| 실제 동작 | 라벨 예시 |
|---|---|
| 상황 입력란으로 이동·포커스 | 연습할 상황 적기 |
| 다음 준비 화면으로 이동 | 연습 준비하기 |
| 대화 세션을 실제로 시작 | 연습 시작하기 |
| 결과 화면 열기 | 피드백 보기 |
| 연습 종류 선택 화면 열기 | 연습 종류 고르기 |
| 실패한 요청 재실행 | 다시 시도하기 |
| 변경 없이 대화상자 닫기 | 닫기 |
| 기록을 실제 삭제 | 기록 삭제하기 |

`확인`, `다음`을 무조건 금지하지는 않는다. 동작이 모호하면 구체적인 이름으로 바꾼다. 삭제 확인의 보조 버튼처럼 창만 닫는 행동을 `취소`로 오해하게 하지 않는다.

### 입력과 검증

- 레이블은 입력 대상, 예시는 입력 형태, 오류는 해결 방법을 알려준다.
- placeholder를 접근성 레이블 대신 사용하지 않는다.
- 실제 최소·최대 글자 수와 안내 숫자를 일치시킨다. 현재 상황 입력은 공백을 제외하는 방식이 아니라 코드의 `trim().length`로 최소 10자를 검사하고 `maxLength={3000}`을 사용한다. 계산 방식을 바꾸면 안내와 검증도 함께 확인한다.
- 검증 오류 예시: `상황을 10자 이상 적으면 다음으로 갈 수 있어요.`
- 면접 예시: `신입 개발자 면접에서 프로젝트 경험을 설명하고 추가 질문에 답하고 싶어요.`
- 직장대화 예시: `팀장에게 일정이 늦어진 이유를 설명하고 먼저 할 일을 정하고 싶어요.`
- 오류가 나도 입력 내용을 지웠다고 단정하거나 실제로 지우지 않는다. 보존 여부를 안내할 때는 구현을 먼저 확인한다.

### 로딩·실패·빈 화면

진행 중에는 현재 작업, 실패 시에는 확인된 문제와 가능한 다음 행동, 빈 화면에는 채울 방법을 알려준다.

| 상태 | 문구 예시 | 적용 조건 |
|---|---|---|
| 대화 생성 요청 중 | 연습할 대화를 만들고 있어요 | 실제 요청이 진행 중일 때 |
| 분석 요청 중 | 대화를 살펴보고 있어요 | 분석 단계가 실제 진행 중일 때 |
| 네트워크 오류 | 연결을 확인하고 다시 시도해주세요 | 연결 오류를 확인했을 때 |
| 원인 불명 생성 실패 | 대화를 만들지 못했어요. 다시 시도해주세요 | 재시도가 가능한 경우 |
| 기록이 없음 | 연습을 마치면 여기에 기록을 모아볼 수 있어요 | 해당 기록 기능을 구현한 경우 |
| 영상 분석 자료 부족 | 표정을 살펴볼 영상이 부족해요 | 실제 분석 상태가 자료 부족인 경우 |

- 근거 없는 완료 시간·진행률·성공 메시지를 표시하지 않는다.
- 서버 응답의 기술 오류·스택 추적·API 키를 사용자 문구로 출력하지 않는다.
- 서버 오류를 사용자 입력 오류처럼 안내하지 않는다.
- 성공 여부를 확인하지 못했다면 `저장했어요`라고 표시하지 않는다.

## 5. AI 대화와 분석 안내

이 장은 Mirror-Ting의 AI 기능을 설명하기 위한 프로젝트 규칙이다.

- AI가 맡는 역할을 분명히 한다. 실제 면접관이나 사람이 응답하는 것처럼 오해하게 하지 않는다.
- 미리 만든 설명 예시는 실제 생성 결과·개인 분석 결과와 구분한다. `설명을 위한 예시예요. 실제 분석 결과는 아니에요.`처럼 안내한다.
- 지원하지 않는 분석 항목이나 제공하지 않는 세부 구간을 약속하지 않는다.
- 표정·자세만으로 감정, 의도, 성격, 업무 능력, 합격 가능성을 확정하지 않는다.
- 분석이 없거나 자료가 부족한 상태를 점수 0으로 표현하지 않는다. 실제 상태를 설명한다.
- 피드백은 사람에 대한 평가보다 관찰한 말과 행동, 다음에 시도할 행동에 집중한다.
- 예: `자신감이 부족해요`보다 `문장 끝의 목소리 크기를 확인해보세요`를 쓴다. 단, 해당 관찰을 실제 분석이 뒷받침할 때만 사용한다.
- 카메라·마이크·저장·전송 안내는 실제 권한과 데이터 흐름에 맞춘다. 확인 없이 `기기에만 저장해요`, `바로 삭제해요`라고 쓰지 않는다.
- 미구현 기업 기능은 `준비 중`임을 밝힌다. 이용·결제·상담이 가능한 것처럼 안내하지 않는다.
- 서비스 UI의 말투와 역할극 속 인물의 말투를 구분한다. 인물의 대사는 시나리오와 관계에 맞게 유지할 수 있지만, 시스템 안내와 혼동하게 하지 않는다.

## 6. 프론트엔드 구현 시 참조 위치

| 영역 | 현재 참조 파일 |
|---|---|
| 히어로, 상황 입력, 입력 검증, 전송 버튼 | `src/pages/HomePage.jsx` |
| 소개 단계와 대화 예시 | `src/components/home/ServiceIntroduction.jsx` |
| 4-Fit 제목과 설명 | `src/components/home/FitAnalysisPages.jsx` |
| 하단 입력 영역 제목과 설명 | `src/components/home/InterviewHome.jsx`, `WorkplaceHome.jsx` |
| 푸터 안내 | `src/components/home/HomeMotion.jsx` |
| 내비게이션 | `src/components/navigation/navigationConfig.js`, `AppNavigation.jsx` |
| 로그인·회원가입과 인증 오류 | `src/pages/AccountPage.jsx`, `src/lib/accountApi.js` |
| 요금제와 준비 중 안내 | `src/pages/PricingPage.jsx` |
| 서비스 소개·사용 방법·연습 기록 | `src/pages/SiteIntroPage.jsx`, `UsagePage.jsx`, `ResultsHistoryPage.jsx` |
| 난이도와 시작 전 확인 | `src/pages/setup/DifficultyPage.jsx`, `src/components/setup/PromptPreflight.jsx` |
| 결과 화면 안내 | `src/pages/ResultPage.jsx` |
| 새 AI 준비 채팅·텍스트 시뮬레이션 | `src/pages/SimulationChatPage.jsx`, `src/lib/simulationChatApi.js` |

- 사용자에게 보여줄 문자열만 수정한다. 문구를 바꾸기 위해 라우트·API 키·상태 값까지 바꾸지 않는다.
- 두 입력창처럼 같은 기능을 재사용하면 안내와 검증 메시지도 함께 확인한다.
- 아이콘 버튼에는 실제 행동을 설명하는 `aria-label`을 제공한다. 보이는 문구와 접근성 이름의 뜻을 맞춘다.
- 오류 안내는 해당 입력과 연결하고 보조 기술에서도 인지할 수 있게 한다.
- 선택 상태나 성공 여부를 색·아이콘·애니메이션만으로 전달하지 않는다.
- 문구가 길어져도 버튼·제목·오류가 잘리지 않는지 모바일에서 확인한다.
- 문구만 바꾸는 작업에 레이아웃·애니메이션·디자인 토큰 변경을 끼워 넣지 않는다.

- [ ] 버튼 이름과 바로 다음 동작이 일치하는가?
- [ ] 제목과 설명의 반복을 줄였는가?
- [ ] 안내는 자연스러운 해요체이고, 용어는 화면 간 일관적인가?
- [ ] 오류가 원인과 다음 행동을 과장 없이 전달하는가?
- [ ] 실제 구현하지 않은 기능·저장·보안·성과를 약속하지 않는가?
- [ ] AI의 역할, 예시와 실제 결과, 분석 한계를 구분했는가?
- [ ] 사용자의 선택을 존중하고 불필요한 재촉을 없앴는가?
- [ ] 메인 히어로 제목과 순환 단어를 별도 요청 없이 바꾸지 않았는가?
- [ ] 모바일 줄바꿈과 접근성 라벨, 빈 화면·오류·로딩 상태를 확인했는가?

새 문구나 용어를 확정하면 관련 UI와 이 문서의 예시를 함께 맞춘다. 실제 기능이나 정책이 바뀌면 기존 문구를 그대로 재사용하지 않고 다시 검토한다.

## 8. AI 준비 채팅과 시뮬레이션

- 웹은 `상황 입력 → AI 준비 채팅 → 설정 확정 → 텍스트 시뮬레이션`으로 이어진다. 예전 난이도·미리보기·대화·결과 화면은 웹에서 다시 연결하지 않는다.
- 준비 항목은 목적, 턴 수, 상황, 대상, 난이도, 성격, 상대 페르소나다. 이미 충분히 입력한 항목은 건너뛰고, 빠진 항목만 순서대로 질문한다. 입력창 위 질문 패널에서 두 가지 예시 응답을 제안하고 직접 입력도 허용한다.
- `1턴`은 사용자 답변 한 번이다. 1~20회 범위를 안내하고 마지막 턴에서는 새 질문을 요구하지 않는다.
- 준비 도우미와 역할극 상대의 말투를 구분한다. 시작 전에는 `준비 도우미`, 시작 후에는 `AI 상대`로 표시한다.
- 설정을 확정하는 버튼은 `설정 확정하고 시작하기`다. 누락 항목이 있으면 해당 이름을 안내하고 시작하지 않는다.
- AI 제공자 전송 동의 전에는 AI 요청을 보내지 않는다. 현재 새 흐름은 텍스트만 사용하므로 카메라·음성 분석을 진행한다고 안내하지 않는다.
- AI 오류가 나면 입력을 유지한다. 실제 모델 응답 없이 고정 대사를 AI가 생성한 것처럼 표시하지 않는다.
