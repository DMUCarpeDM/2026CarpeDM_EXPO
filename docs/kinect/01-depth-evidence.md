## 0. 한 문장

**브라우저 MediaPipe가 2D 영상에서 물리적으로 낼 수 없는 축을, 뎁스 센서로 실측한다.**

"카메라를 더 좋은 걸 썼다"가 아니다. **측정 가능한 물리량의 종류 자체가 다르다.**

## 1. 왜 2D로는 안 되는가 — 축별 대조

| 지표 | MediaPipe (2D 영상) | 뎁스 (Kinect) | 근거 |
|---|---|---|---|
| **몸통 회전** (`torso_yaw_deg`) | **원리적으로 불가.** 어깨폭이 줄어드는 것으로만 보여서 "몸을 틀었다"와 "뒤로 물러났다"가 구분되지 않는다 | 어깨선 3D 벡터에서 직접 | [구현] `geometry.py:102` |
| **고개 각도** (`head_pitch_deg`) | `eyeLookDown` blendshape = **안구가 아래를 보는 정도**. 고개 각도가 아니다 | 목→머리 3D 벡터의 실제 각도 | [구현] `geometry.py:114` |
| **어깨 기울기** | 비스듬히 선 사람의 어깨가 기울어 보이는 고질 오차 (yaw가 tilt로 샘) | **yaw 불변** — 3D에서 y성분만 보므로 회전이 안 섞임 | [구현] `geometry.py:89` |
| **상체 전후 이동** | 어깨폭 프록시 → 체격에 따라 스케일이 달라 **사람 간 비교 불가** | 절대 cm | [구현] `geometry.py:129` |
| **좌우 흔들림** | 어깨너비로 정규화한 무단위 비율 | 실제 cm — 리포트에 그대로 쓸 수 있다 ("답변 중 평균 4.2cm") | [구현] `geometry.py:138` |
| **등 굽음** (`spine_bend_mm`) | **불가.** 관절 3개로는 직선밖에 안 나온다 | 포인트 클라우드를 8층으로 잘라 각 층 중심을 이은 곡선 | [구현] `surface.py:171` |
| **누구를 재는가** | `numFaces:1` — 잡히는 얼굴을 아무거나. 관람객이 몰리면 뒷사람을 잴 수 있다 | 바디별 3D 거리로 **거울 앞 1~2m 안의 가장 가까운 사람만** | [구현] `device.py:87` |

> 마지막 항목이 전시 현장에서 가장 크게 체감되는 차이다. 부스에 사람이 몰릴수록 벌어진다.

## 2. 실측 근거 — 실기기에서 실제로 잰 것

전부 **S/N 000246214712** 실기기, **2026-07-27** 측정. 출처는 소스 주석.

### 2.1 중력 정렬이 실제로 맞는지 [실측]

카메라를 미러 상단에 아래로 틸트해 달면 raw Y축이 수직이 아니다. **이 상태로 어깨 기울기를 재면 거치 각도가 점수에 그대로 섞인다.** 그래서 IMU 가속도계로 중력을 구해 세계 좌표계로 옮긴 뒤 잰다.

| 검증 | 결과 |
|---|---|
| 정지 60표본, 수평 거치 가정의 위 벡터 `(0,-1,0)`와 내적 | **+0.999** |
| 같은 표본, 관절 기반 정답(머리−골반)과 내적 | **+0.999** |

**두 개의 독립된 근거가 같은 방향을 가리켰다.** 하나는 물리(IMU), 하나는 기하(관절) — 서로의 검산이다.

> 여기에 함정이 하나 있고, 코드가 그걸 잡았다: 가속도계는 중력이 아니라 그 **반작용**(proper acceleration)을 읽는다. 정지 상태에서 벡터는 '아래'가 아니라 **'위'**를 가리킨다. 부호를 착각하면 세계 좌표계가 통째로 뒤집혀 **고개 각도가 180도 어긋난다.** — `geometry.py:26`

### 2.2 관절 경로 vs 표면 경로 교차검증 [실측]

같은 몸을 **완전히 독립된 두 방법**으로 잰다.

| 경로 | 입력 | 정면 정지 150프레임 yaw 지터 |
|---|---|---|
| 관절 | k4abt DNN이 낸 관절 32개 | **0.202°** |
| 표면 | 포인트 클라우드 최대 26만 점 | **0.223°** |

**두 방식의 계통 차이: 0.7°**

이게 왜 중요한가 — "이 숫자를 왜 믿느냐"에 대한 답이 된다. 서로 다른 원리의 두 측정이 0.7° 안에서 일치한다는 것은, 값이 특정 알고리즘의 산물이 아니라 **실제 몸의 기하**라는 뜻이다.

> **정직 포인트:** 표면 경로가 더 정밀해서 도입한 게 아니다. 실측에서 **표면이 오히려 약간 시끄러웠다**(0.223 > 0.202). k4abt 관절은 이미 DNN이 실루엣 전체를 소비해 만든 값이라 충분히 평활하고, ToF 노이즈는 공간 상관이 있어 점을 늘려도 √N으로 줄지 않는다. 표면 경로의 가치는 **교차검증**과 **관절로는 못 내는 양**(등 굽음·면적 가중 중심)이다. — `surface.py:3`

### 2.3 유효 거리 하한을 실측으로 정함 [실측]

700프레임, 43~207cm 구간에서 척추 시상면 편차를 잰 결과:

| 거리 | 척추 편차 |
|---|---|
| 100cm 이상 | **26.9 ~ 32.8mm** (평탄) |
| 100cm 미만 | **−31.7 ~ +57.4mm** (요동) |

100cm 아래에서는 골반이 프레임에서 잘려 몸통 띠 정의가 깨진다. → `KIOSK_NEAR_MM = 1000`

> **[미검증]** 전시 설계가 '미러 앞 1m'이라 정확히 경계선이다. **리그 완성 후 실제 거치 높이에서 재확인이 필요하다.** — `device.py:26`

### 2.4 몸통 상단 절단 위치를 실측으로 정함 [실측]

700프레임, 91~206cm에서 **목·승모근이 가슴보다 약 38mm 뒤**에 있음을 확인. 목 높이까지 몸통으로 잡으면 척추 곡선의 위쪽 끝이 뒤로 끌린다. → `TORSO_TOP_FRACTION = 0.75` (골반→목 구간의 75%에서 절단)

### 2.5 평면 적합을 폐기한 이유 [실측]

처음엔 몸통에 평면을 맞춰 회전을 내려 했다. 실기기에서 **planarity 0.63**으로 임계(0.45)를 넘어 **각도가 100% 억제**됐다 — 몸통은 평면이 아니다. 흉골~복부의 시상면 곡률이 가장 큰 구간이 하필 수직 중심띠다.

→ 가슴 높이 **수평 띠**를 위에서 내려다본 (x, z) 산포의 주축(SVD)으로 교체. 곡률에 영향받지 않는다. — `surface.py:132`

### 2.6 성능 [실측]

| 항목 | 값 |
|---|---|
| 바디 트래킹 | **CUDA 23.4ms/프레임 (≈43fps)** — RTX 3060 |
| 운용 fps | 30fps (여유 있음) |
| 뎁스 모드 | WFOV_2X2BINNED — 1m에서 수직 **3.46m** 커버 |

> NFOV는 1m에서 1.27m라 허리에서 잘린다. k4abt는 전신 실루엣으로 학습된 모델이라 하반신이 잘리면 PELVIS·SPINE_NAVEL이 **관측이 아니라 외삽**으로 채워진다. — `device.py:3`

## 3. "근거 없는 숫자를 만들지 않는다" — 코드에 박힌 정직성 장치

심사에서 이 부분이 기술 자랑보다 강하다. 전부 [구현] 확인.

| 장치 | 내용 | 위치 |
|---|---|---|
| **밴드 없으면 점수 없음** | 신규 지표(`torso_yaw`·`head_pitch`·`torso_lean`·`spine_bend`)는 `bands=None` → 화면에 "채점 밴드 없음"으로 표시. **근거 없는 밴드를 발명하지 않는다** | `service.py:93` |
| **단위가 다르면 환산하지 않음** | 고개 각도(도)를 `head_down_ratio` 밴드(프레임 비율)에 넣지 않는다. "근거 없는 환산을 만들지 않는다" | `service.py:_posture_live` |
| **빠진 성분을 숨기지 않음** | 실시간 Posture-Fit이 순간값으로 못 내는 성분(고개 숙임 0.35·자세 유지력 0.15)을 `missing`으로 **함께 내려보낸다** | `service.py:_posture_live` |
| **측정 보류에 이유를 붙임** | 표본 부족·거리 이탈 시 null + 사유(`no_body`/`too_close`/`too_far`/`unstable`). "화면이 조용히 비면 원인을 알 수 없다" | `service.py:114` |
| **예측값을 지표에 안 씀** | `K4ABT_JOINT_CONFIDENCE_MEDIUM` 미만은 "가려져서 예측만 한" 값이라 배제 | `device.py:55` |
| **단일 출처** | 발표 화면의 점수를 **서버의 실제 채점 함수**로 계산해 내려보낸다. 화면이 밴드를 재구현하면 숫자가 갈라진다 | `service.py:93` |
| **최소 표본 게이트** | 평면 200점 · 띠 30점 · 곡선 4층 미만이면 측정 자체를 보류 | `surface.py:30` |

**자동화 테스트 53개 전부 통과** (`test_kinect_geometry.py` + `test_kinect_surface.py`, 2026-07-29 실행 확인). 하드웨어 없이 도는 순수 numpy 테스트라 CI에 넣을 수 있다.

## 5. 심사 답변 카드

### "왜 웹캠이 아니라 키넥트입니까?"

> 정확도를 올리려던 게 아니라, **2D로는 낼 수 없는 축이 있어서**입니다. 예를 들어 몸을 옆으로 트는 건 회피 신호인데, 2D 영상에서는 어깨폭이 줄어드는 것으로만 보여서 '뒤로 물러난 것'과 구분이 안 됩니다. 뎁스는 이걸 각도로 직접 줍니다. 고개 각도도 마찬가지로, 기존 방식은 안구가 아래를 보는 정도였지 실제 목 각도가 아니었습니다.

### "그 숫자를 왜 믿습니까?" ★

> 완전히 독립된 두 경로로 같은 몸을 잽니다. 하나는 관절 32개, 하나는 포인트 클라우드 26만 점입니다. 정면 정지 150프레임에서 두 방식의 계통 차이가 **0.7도**였습니다. 원리가 다른 두 측정이 그 안에서 일치한다는 건, 값이 특정 알고리즘의 산물이 아니라 실제 몸의 기하라는 뜻입니다.

### "카메라를 기울여 달면 각도가 틀어지지 않습니까?" ★

> 정확히 그게 저희가 가장 먼저 해결한 문제입니다. 미러 상단에 아래로 틸트해 달면 센서 Y축이 수직이 아니라서, 그대로 재면 **거치 각도가 점수에 섞입니다.** 그래서 IMU 가속도계로 중력을 구해 세계 좌표계로 옮긴 뒤에 잽니다. 이게 맞는지도 두 가지로 확인했습니다 — 수평 거치 가정과 내적 0.999, 관절 기반 정답과도 0.999였습니다.

### "새로 측정한 지표들은 점수에 어떻게 반영됩니까?"

> **아직 반영 안 합니다.** 채점 밴드의 근거가 없어서 관찰 지표로만 두고 있고, 화면에도 '채점 밴드 없음'으로 표시됩니다. 근거 없는 임계값을 만드는 게 더 위험하다고 판단했습니다. 밴드는 실측 표본이 쌓인 뒤에 붙일 계획입니다.

### "관람객이 몰리면 누구를 측정합니까?"

> 뎁스가 사람마다 3D 거리를 주기 때문에, **거울 앞 1~2m 안의 가장 가까운 사람 한 명**만 고릅니다. 2D 얼굴 인식은 잡히는 얼굴을 아무거나 재기 때문에 부스에 사람이 몰릴수록 뒷사람을 잴 위험이 있는데, 그게 없습니다.
