## 1. 왜 절반만 대체되는가 — 아키텍처 사실 [구현]

k4abt(바디 트래킹)가 주는 것은 **관절 32개**다. **홍채·눈꺼풀·표정 blendshape는 주지 않는다.**

| Fit | 입력 | 키넥트로 대체 가능? |
|---|---|---|
| **Posture-Fit** | 어깨·목·머리·골반 관절 위치 | ✅ **전면 대체 가능.** 오히려 우월 (`01-depth-evidence.md` §1) |
| **Eye-Fit** | 홍채 위치·눈꺼풀·`eyeLookDown` blendshape·깜빡임 | ❌ **불가.** k4abt에 없는 데이터 |
| 표정·긴장 | FaceLandmarker blendshape | ❌ 불가 |
| Voice-Fit / Response-Fit | 오디오·텍스트 | 무관 |

> 이건 이미 코드가 인정하고 있다 — `service.py:43`이 MediaPipe 에셋(`vision_bundle.mjs`·wasm·models) 경로를 잡아 얼굴 메쉬 데모 페이지(`static/face.html`)를 띄운다. **처음부터 하이브리드 전제로 짜여 있었다.**

**따라서 S6는 "교체"가 아니라 "분업"이다.**

```
키넥트 뎁스  →  Posture-Fit  (어깨·몸통·척추)
웹캠+MediaPipe →  Eye-Fit    (시선·홍채·깜빡임·표정)
                     ↓
              같은 NonverbalIn 페이로드
```

## 2. 배선 설계

### 2.1 이음새는 `NonverbalIn` 스키마다 [설계]

기존 채점(`app/ai/nonverbal.py`)을 **한 줄도 고치지 않는다.** 생산자만 바꾼다. 이건 `__init__.py`가 이미 선언한 방침이다 — *"기존 백엔드 채점은 그대로 두고, NonverbalIn 페이로드를 채우는 '생산자'만 옮기는 구조"*.

### 2.2 필드별 매핑 — 여기가 실제 작업이다

| `NonverbalIn` 필드 | 키넥트 대응 | 난이도 |
|---|---|---|
| `posture_sway` | `sway_norm` (어깨너비 정규화) | ✅ **그대로.** `service.py`가 이미 cm와 정규화값을 둘 다 낸다 |
| `avg_shoulder_tilt_deg` | `shoulder_tilt_deg` | ⚠️ **개인 기준 보정 필요** (§2.3) |
| `tilt_drift_deg` | 턴 전·후반 평균 차 | ⚠️ 키넥트 서비스가 턴 단위로 누적해야 함 |
| `head_down_ratio` | `head_pitch_deg` | ❌ **단위가 다르다** (§2.4) — 최대 난관 |
| `frames` | 프레임 카운트 | ✅ 그대로 (`MIN_FRAMES = 5` 게이트 유지) |
| 시선 계열 전부 | — | 브라우저가 계속 채움 |

### 2.3 개인 기준 보정을 키넥트 쪽에도 옮겨야 한다 [갭]

현재 브라우저는 브리핑 중 자세를 캘리브레이션하고 **`max(0, 현재 − 개인기준)`**으로 보정한다 (`useNonverbal.ts:457`). 이게 척추측만·비대칭 체형에 대한 유일한 방어이자, `03-validity-bias-qa.md` Q30 답변의 근거다.

**키넥트 경로에 이게 없으면 그 답변이 거짓이 된다.** 반드시 이식할 것:

```
브리핑 시작 → 키넥트 서비스에 "캘리브레이션 시작" 신호
브리핑 종료 → 표본 4개 이상이면 중앙값으로 base.tilt 확정 (브라우저와 동일 규칙)
                표본 부족 → set=false → 절대 판정 유지 (브라우저와 동일)
```

> 중앙값·최소 표본 4개·`max(0, ...)`까지 **브라우저 구현과 규칙을 똑같이** 맞춘다. 두 경로가 다른 규칙을 쓰면 폴백 전환 시 점수가 튄다.

### 2.4 `head_down_ratio` — 근거 없이 환산하면 안 되는 지점 ❗

| | 물리량 | 값 |
|---|---|---|
| 기존 | 프레임 **비율** — 고개가 내려간 프레임 / 전체 | 0~1 |
| 키넥트 | 실제 **각도** — 목→머리 벡터 | 도(°) |

`service.py`가 이걸 정확히 지적하고 거부했다 — *"그 밴드는 '프레임 비율' 기준이라 단위가 다르다. 근거 없는 환산을 만들지 않는다."*

**환산하려면 임계 각도 θ가 필요하다** — "pitch > θ면 고개 숙임 1프레임". 그런데 θ를 발명하면 지금까지 지킨 정직성이 무너진다.

**[설계] 근거 있는 θ를 얻는 방법 — 동시 측정 대조**

두 센서를 **동시에** 돌리고, MediaPipe가 `headDown=true`로 판정한 프레임과 키넥트 `head_pitch_deg`를 짝지어 기록한다. 그러면 θ는 발명이 아니라 **"기존 판정을 가장 잘 재현하는 값"**으로 유도된다.

- 필요한 것: 동시 기록 세션 수십 개 (자원자 5~10명 × 각 3~5턴이면 충분)
- 이미 도구가 있다: `playback.py` — *"밴드·임계값을 실측 기반으로 튜닝할 수 있으며, CI에 넣을 수도 있다"*
- 산출물: θ + 일치율. **일치율도 함께 발표하면** "기존 지표와 호환된다"는 주장이 검증 가능해진다

> 이 대조 연구는 Q17의 "8월 예비 연구"와 **같은 세션에서 같이 돌릴 수 있다.** 자원자를 두 번 모으지 않아도 된다.

### 2.5 폴백 — 지우지 말 것 ❗❗

**Azure Kinect DK는 2023년 단종됐다.** 고장 시 조달이 불가능하고, 4일 연속 전시에서 단일고장점이다.

```
키넥트 정상  →  Posture-Fit = 뎁스 경로
키넥트 부재·오류·거리 이탈  →  Posture-Fit = 기존 MediaPipe 경로 (현행 그대로)
```

**MediaPipe 자세 코드를 제거하지 않는다.** 이건 최적화가 아니라 생존 요건이다. LRR의 "폴백은 시연의 생명" 원칙 그대로고, `02-halfmirror-ir-verification.md` 대안 3이 상시 살아 있어야 하는 이유이기도 하다.

전환은 `GET /api/health`에 `kinect` 필드를 추가해 운영자가 상태를 볼 수 있게 한다 (기존 `server_stt`와 같은 패턴).

### 2.6 프로세스 구조

현재 키넥트 서비스는 `:8002` 별도 프로세스다. **이 분리를 유지하는 걸 권장한다.**

- 키넥트 드라이버가 죽어도 전시 서버(`:8001`)가 안 죽는다
- ctypes + CUDA 초기화가 메인 서버 기동을 늦추지 않는다
- 대가: 프로세스 간 통신 한 겹. 하지만 **로컬 WebSocket이라 비용이 무시할 수준**이고 이미 동작한다

## 3. 신규 지표에 밴드를 붙일 것인가 (E)

### 3.1 현재 상태 [구현]

| 지표 | 밴드 | 화면 표시 |
|---|---|---|
| `torso_yaw_deg` (몸통 회전) | 없음 | "신규 · 뎁스로만 가능" |
| `head_pitch_deg` (고개 각도) | 없음 | "신규 · 실제 목→머리 각도" |
| `torso_lean_deg` (상체 기울기) | 없음 | "표면 · 척추선 전체 기울기" |
| `spine_bend_mm` (등 굽음) | 없음 | "표면 · 검증 진행 중 (해석 확정 전)" |

### 3.2 판단 — 8/4 전에는 붙이지 않는다

**이유 세 가지:**

1. **근거가 없다.** 어깨 기울기 6도는 참고치라도 있었지만, "몸통을 몇 도 틀면 회피인가"는 참조할 곳이 없다. 발명하면 Q18·Q34 답변이 무너진다.
2. **지금 상태가 오히려 강점이다.** "밴드 없음"이 화면에 표시되는 것 자체가 §Q34의 답이다 — *"근거가 약한 지표는 점수에 안 넣습니다"*를 말이 아니라 **화면으로** 증명한다.
3. **점수에 안 들어가도 리포트에 쓸 수 있다.** 관찰 문장으로는 지금도 쓸 수 있다: *"답변 중 몸이 평균 12도 왼쪽으로 돌아가 있었습니다"* — 점수 없이 관측만 서술하는 건 **"감점이 아니라 관찰"** 원칙에 정확히 맞다.

> ⚠️ **다만 한 가지 위험:** 리포트에 아예 안 나타나면 관람객은 그 축이 존재하는지도 모른다. **점수는 안 붙이되 관찰 문장으로는 노출하는 것**을 권한다. 이게 §3.2의 3번이고, 구현 비용도 가장 싸다.

### 3.3 10월 이후 밴드를 만든다면 — 절차 [설계]

**발명하지 말고 분포에서 유도한다.**

1. **표본 수집** — 8/4 이후 전시·리허설에서 `playback.py`로 세션 녹화 누적
2. **분포 확인** — "정상 범위"를 백분위로 정의. 예: 몸통 회전은 중앙 80% 구간을 무감점, 상위 10%부터 관찰 문장
3. **최소 N 게이트** — 표본이 적으면 밴드를 활성화하지 않는다. 기존 코호트 백분위가 이미 신뢰 라벨로 방어하는 것과 같은 패턴 [구현]
4. **CI 회귀** — 녹화본을 테스트 픽스처로 삼아 밴드 변경 시 점수 변화를 확인. `playback.py` 주석이 이미 예고한 용도다

> **분포 기반 밴드의 한계도 문서에 적어둘 것:** "많은 사람이 하는 것 = 좋은 것"이 아니다. 이건 규범적 근거가 아니라 **관찰 기준**이므로, 점수보다 관찰 문장에 쓰는 게 정직하다.

## 4. 접근성 — 자세 항목 비활성화 토글 [갭]

`03-validity-bias-qa.md` Q31(휠체어)의 후속. 현재는 게이트에 걸려 **자동 배제**되므로 틀린 값이 나오진 않지만, 관람객 입장에서는 "왜 이 항목이 비었는지" 알 수 없다.

**[설계] 최소 구현:** 운영자 패널(`OperatorPanel.tsx` 기존)에 자세 항목 비활성화 스위치. 켜면 Posture-Fit을 측정 보류로 고정하고, 리포트에 *"이번 체험에서는 자세 항목을 측정하지 않았습니다"*로 명시.

- 비용: 낮음 (기존 측정 보류 경로 재사용)
- 효과: Q31 답변이 "아직 없습니다"에서 "이렇게 대응합니다"로 바뀐다
- 시점: 10월 전. 8/4 발표에서는 **계획으로 언급**하는 것으로 충분

## 6. 한 줄 요약
