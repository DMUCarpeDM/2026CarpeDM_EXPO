# 발화 종료 → 다음 AI 대사 지연 진단

사용자 관찰: 실제 음성 대화에서 말이 끝난 뒤 다음 AI 대화까지 약 7초.

## 코드에서 확인한 경로

말 끝 → 브라우저 SpeechRecognition final 이벤트 → 750ms 자동 제출 대기 → /response API (완성된 AI 대사 전체 수신) → /tts 요청 → 첫 PCM 청크 → 오디오 재생 및 자막 표시.

- sttAutoSubmit.js: AUTO_SUBMIT_DELAY_MS=750.
- usePracticeTranscription.js: isFinal이며 미확정 텍스트가 없을 때만 자동 제출 예약. 미확정 텍스트가 오면 타이머 취소. 이는 마지막 소리부터 750ms가 아니라 브라우저 문장 확정부터 750ms다. 인식기가 늦게 확정하면 그 시간은 별도로 더해진다.
- openai_provider.py: stream 없이 완성된 chat/completions 본문을 기다린다.
- turnSpeechPlayback.js: 대사 수신 후 별도 TTS 요청을 한다. PCM은 첫 청크부터 재생하므로 전체 음성 파일을 기다리지는 않는다.
- MirrorSubtitles.jsx: waiting 상태에서 자막 숨김, playing/ended 때 표시. 텍스트 수신과 자막 표시가 같은 시점이 아니다.
- pocApi.js 및 sessions.py: workplace_continuous는 다음 AI 오디오가 시작된 뒤 녹음 업로드를 풀고, 상세 채점은 뒤로 미룬다. 현재 다음 대사 생성이 녹음 업로드/Whisper/상세 채점 완료를 기다리는 경로는 아니다.

## 실제 측정 (3회)

동작 중 로컬 8001의 실제 세션 응답 API에 가상 텍스트를 제출했다. OpenAI에는 이전에 승인된 가상 답변만 전송했다. 음성 API에는 개인정보나 프로젝트 프롬프트 없는 고정 일반 문장만 사용했다. 생성문은 32/34/47자였고 음성 측정 문장은 별도 고정 문장이므로 실제 발화와 완전히 동일한 종단간 테스트는 아니다.

| 회차 | 응답 API 완료 | TTS 첫 1024바이트 | TTS 전체 전송 완료 | +750ms 합계 |
|---|---:|---:|---:|---:|
| 1 | 2.196초 | 0.432초 | 1.109초 | 3.378초 |
| 2 | 1.090초 | 0.414초 | 1.191초 | 2.254초 |
| 3 | 1.459초 | 0.445초 | 1.384초 | 2.654초 |

응답 API 시간에는 DB/진행 처리 및 네트워크가 포함돼 있으며 순수 OpenAI 추론 시간으로 분리해 측정하지 않았다. 첫 음성 바이트와 실제 스피커 출력 사이의 AudioContext/재생 처리도 이 측정에는 없다. TTS 전체 전송 시간은 첫 소리 대기 시간에 더하면 안 된다.

## 결론과 한계

약 7초라는 사용자 관찰을 기준으로 하면 이번 제어 측정에서 설명되지 않는 시간이 약 3.6~4.7초다. 발화 종료→SpeechRecognition final 확정 지연이 주요 의심 구간이며, 브라우저의 프레임/오디오 재생 지연과 외부 서비스 시간 변동도 가능하다. 현재 탭은 체험 전 안내 화면이어서 실제 발화 끝 시점과 final 이벤트 사이를 직접 재지 못했다. 따라서 7초 중 몇 초가 인식기에 속하는지 확정하지 않는다.

다음 실측은 마지막 음성 신호, final 이벤트, 제출 시작, 응답 도착, TTS 요청, 실제 onStart를 같은 브라우저 시계로 기록해야 한다. 이후 종료 감지 및 제출 대기, 텍스트/TTS 순차 처리, 자막 표시 대기를 순서대로 조정할 수 있다. 현 진단에서는 제품 코드를 수정하지 않았다.
