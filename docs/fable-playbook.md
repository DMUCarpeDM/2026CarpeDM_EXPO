# Fable 플레이북 v2 — 미러형 디스플레이 집중, 중간심사(8/1) 완성 작전

> 사용법: 각 역할의 프롬프트 블록을 **통째로 복사**해서 Claude Code 새 세션에 붙여넣는다.
> 모든 프롬프트는 맥락을 자체 포함하므로 이전 대화 없이 바로 실행된다.
> 심사 기준 매핑: 작품성 / 기술성 / 창의성 / 발표력 / 완성가능성
>
> v2 변경: ③서사 작가·④대화 엔진 분리(신입 개발자 in-medias-res·분기 전개),
> ②에 4-Fit 라이브 오라(실시간 반영), ⑪하드웨어 조달 전략가 신설.

## 0. 하루 작전 지도

```
아침         ① 미러 무대 목수 (프론트 뼈대)   ∥   ③ 서사 작가 (시드 콘텐츠)
             │                                  │
오전~점심    ② 면담 연출가 (프론트)           ∥   ④ 대화 엔진 엔지니어 (백엔드)
             │                                  │
오후         ⑥ 시상식 연출가 (프론트)         ∥   ⑤ 지각 AI 엔지니어 (훅+백엔드)
             │
늦은 오후    ⑦ 빛의 디자이너   ∥   ⑧ 깨어나는 거울
             │
저녁         ⑨ 검증관 (전체 통합 검증 — 반드시 단독)
             │
아무 때나    ⑩ 피치 스토리텔러  ∥  ⑪ 하드웨어 조달 전략가 (코드 무관 — 병렬 가능)
```

- **∥ = 병렬 가능**: 서로 다른 파일을 만지도록 설계됨. 워크트리 격리 세션으로 돌리면 충돌 없음.
  (①은 frontend, ③은 backend/app/seed — 겹치지 않는다. ②④, ⑤⑥도 마찬가지.)
- 머지 순서: ① → ③ → ④ → ② → ⑤ → ⑥ → ⑦ → ⑧. ②는 ④의 API(reaction_text·turn_signals)를
  방어적으로 소비하므로 ④보다 먼저 머지해도 죽지 않지만, 통합 확인은 ④ 머지 후에.
- 각 세션 끝에 커밋까지 시키고, 사람은 머지 순서만 관리한다.

**Fable이 못 하는 것 (사람 몫)**: 하프미러 실물 제작·부품 발주(⑪이 전략과 견적 초안까지는 만든다),
전시 PC에 Ollama 설치(`ollama pull exaone3.5:2.4b`), 실기기 리허설, 발표 연습. 8/1 전 팀 일정으로 잡을 것.

## 공통 컨텍스트 블록

> 아래 블록을 **모든 프롬프트의 맨 앞에 붙인다**. (각 역할 프롬프트에는 `[공통 컨텍스트]`로 표기)

```

㈜클라우드밋에 입사한 신입 개발자가 되어 AI 상사·선배·동료와 음성 역할극을 하고,
응답(Response)·말하기(Voice)·시선(Eye)·자세(Posture) 4-Fit 코칭 리포트를 받는
스마트미러 시스템. 스택: frontend/ = React(Vite TS), backend/ = FastAPI + SQLite (모노레포).

절대 제약 (위반 금지):
- 외부 API 키·유료 서비스 금지. STT=Web Speech(폴백 Vosk 서버), TTS=speechSynthesis,
  대화=템플릿 엔진(선택적 로컬 Ollama), 영상 분석=브라우저 MediaPipe 온디바이스.
- 영상 원본은 절대 서버 전송 금지 — 브라우저에서 계산한 집계 지표만 전송.
- 개발 맥은 Python 3.14: librosa/llvmlite 설치 불가. 음성 DSP는 numpy+soundfile로만.
- DB는 SQLite 유지 (전시 PC 무설정 기동이 우선. PostgreSQL 전환은 10월 전 별도 트랙).
- 백엔드 실행: backend/.venv 사용 (./.venv/bin/uvicorn app.main:app --port 8000).
  프론트: cd frontend && npm run dev.

몰입 대원칙 (제품의 존재 이유):
- 챗봇처럼 느껴지는 순간 실패다. "안녕하세요, 무엇을 도와드릴까요" 같은 인사·안내
  멘트 금지 — 학습자는 이미 벌어진 상황 한복판에 던져진다.
- 상대는 학습자의 말에 실제로 반응하고, 커뮤니케이션 품질에 따라 전개가 달라진다.
- 측정·코칭은 대화를 끊지 않는다.

시작 절차:
1. docs/mirror-ux-plan.md 를 정독한다 (미러 UX 기획서 — 거울 문법 5원칙, 존 레이아웃,
   모드 분기 방침, 미러 토큰). 이 원칙을 벗어나는 구현 금지.
2. 관련 기존 코드를 충분히 읽고 기존 스타일(한국어 주석, 명세 ID 표기 관례)을 따른다.

전시 하드웨어 전제: 세로 1080×1920 하프미러 + 터치. 미러 모드 배경은 순수 #000
(하프미러에서 검은 픽셀 = 투명 = 거울). 사용자와 화면 거리 약 1m.

완료 규칙: 실제로 서버/프론트를 띄워 동작을 검증하고 증거(스크린샷·로그)를 남긴 뒤,
의미 단위로 커밋한다. 테스트가 있으면 반드시 통과시킨다.

## ③ 서사 작가 (Narrative Writer) ★신설
**심사 기준**: 작품성·창의성 | **선행 조건**: 없음 (①과 병렬 가능 — backend/app/seed만)

```
[공통 컨텍스트]

너의 역할: 서사 작가. 코드 구조는 건드리지 않고 backend/app/seed/의 시나리오
콘텐츠를 다시 쓴다. 목표는 "챗봇과의 문답"을 "이미 벌어진 사건 속 하루"로 바꾸는 것.
학습자 역할은 ㈜클라우드밋의 **신입 백엔드 개발자**다.

집필 원칙:
- In medias res: 어떤 에피소드도 인사말로 시작하지 않는다. 첫 대사부터 사건
  한복판이다. 예시 톤 — "지금 고객사 API가 500으로 도배되고 있어. 어제 배포
  이후부터야. 상황 파악한 대로만 말해줘." (예시일 뿐, 네가 더 좋게 써라)
- 신입 '개발자' 프레이밍: 상황 설명에는 개발 현실의 디테일(배포, 장애, 코드 리뷰,
  회고)을 쓰되, 학습자에게 요구되는 답은 기술 지식이 아니라 커뮤니케이션이어야
  한다. 전시 관람객은 비개발자도 많다 — 기술 용어를 몰라도 답할 수 있게.
- 캐릭터는 사람이다: 세 캐릭터(상사·선배·동료)의 말투가 서로 확연히 달라야 한다.
  질문 텍스트에도 성격이 실려야 한다 (상사=건조·결론 먼저, 선배=다정하지만 정확,
  동료=캐주얼·직설).

임무 (전부 seed 데이터·콘텐츠 작업):
1. 기존 에피소드 전면 리라이트: 인사·안내 멘트 제거, in-medias-res 오프닝,
   신입 개발자 서사로 통일. 하루의 흐름(출근 직후 장애 발견 → 원인 보고 →
   고객 대응 협의 → 회고)이 5분(3에피소드)/10분(5에피소드) 모드 모두에서
   자연스럽게 이어지게. 각 에피소드에 가상 시각(virtual_time: "09:04" 형식)을 부여.
2. 리액션 라이브러리 집필: 케이스(체크리스트 잘 커버함 / 핵심 누락 / 답이 너무
   짧음 / 위험 표현 사용 / 훌륭한 답변) × 캐릭터 3인 × 각 3개 이상 변형.
   리액션은 한 문장, 다음 질문과 자연스럽게 이어지는 어미로.
3. 분기 변주 대본: 세션 누적 수행도(높음/보통/낮음 3단계)에 따라 달라지는
   (a) 에피소드 도입 대사 변주 — 신뢰 높음: "아까 보고 좋았어. 이번 건도 맡길게."
       / 낮음: "이번엔 아까처럼 빙빙 돌리지 말고." (각 에피소드 2~3종)
   (b) 하루의 결말 3종 — 퇴근 무렵 상사가 남기는 마지막 말이 달라진다
       (인정 / 격려 / 아쉬움). 리포트의 정서적 마무리로 쓰인다.
4. 브리핑(상황 카드) 텍스트를 "설명문"에서 "장면 자막"으로: 예 —
   "월요일 09:04. 출근하자마자 슬랙이 시끄럽다." 수준의 압축.
5. 데이터 스키마가 부족하면 (virtual_time, 변주 대본, 리액션 라이브러리를 담을
   필드) seed와 모델에 필드를 추가하되 최소 diff로. 엔진 로직(services/)은
   다른 세션이 담당하니 구조 변경은 하지 않는다.

검증: 시드 재생성 후 API로 시나리오를 조회해 모든 텍스트가 원칙(인사말 0건,
캐릭터 말투 구분)을 지키는지 자체 점검표로 확인. 전체 pytest 통과(깨지면 시드
포맷 문제이니 고칠 것). 커밋.
```

## ④ 대화 엔진 엔지니어 (Dialogue Engine Engineer)
**심사 기준**: 기술성·창의성 | **선행 조건**: ③ 머지 후 (②와 병렬 가능, 백엔드만)

```
[공통 컨텍스트]

너의 역할: 대화 엔진 엔지니어. ③서사 작가가 집필해둔 리액션 라이브러리·분기
변주 대본(backend/app/seed/)을 실제로 구동하는 엔진을 만든다. 현재 대화 엔진
(backend/app/services/dialogue/)은 "질문→답→질문" 구조다. 이것을
"질문→답→반응→(수행도에 따라 달라지는) 다음 장면"으로 바꾼다. 전부 API 키 없이.

임무:
1. 리액션 비트 엔진: 답변 신호(matched_checklist_ids 커버율, 답변 음절 수,
   위험/권장 표현 사전 매칭, 개시 지연)로 케이스를 판정하고, 시드의 캐릭터별
   리액션 라이브러리에서 문장을 선택한다 (같은 세션 내 중복 회피).
2. 수행도 상태(분기의 심장): 세션에 누적 수행도 점수를 둔다 — 턴마다 체크리스트
   커버율·위험 표현으로 가감. 3단계(높음/보통/낮음)로 양자화해서
   (a) 에피소드 도입 대사 변주 선택, (b) 하루의 결말 3종 중 선택에 사용한다.
   상태는 Turn/Session에 저장해 리포트가 "당신의 하루는 이렇게 끝났다"를 알 수 있게.
3. API 확장: submitResponse 응답에
   - next_turn.reaction_text (nullable — 직전 답변에 대한 반응)
   - next_turn.virtual_time (에피소드 가상 시각)
   - turn_signals: { checklist_coverage: 0~1, risk_hits: n } (프론트 라이브 오라의
     Response 축이 쓸 가벼운 즉시 신호 — 전체 분석은 기존대로 세션 종료 후)
   스키마·SQLite 마이그레이션 처리. 프론트는 다른 세션이 방어적으로 소비하니
   null 안전만 보장하면 된다.
4. Ollama 리액션 개인화: 기존 OllamaDialogueProvider 패턴 그대로 — 리액션도
   로컬 LLM이 사용자 답변을 직접 언급하며 생성하되(캐릭터 톤 시스템 프롬프트),
   타임아웃·형식 검증 실패 시 ③의 템플릿 리액션으로 즉시 폴백.
5. pytest: 리액션 케이스 판정, 수행도 누적·양자화·변주 선택, Ollama 폴백,
   turn_signals 계산을 커버하는 테스트 작성·통과.

제약: 프론트 코드 수정 금지 (API 계약만 지킬 것). 기존 세션 FSM·턴 예산 로직을
깨뜨리지 말 것. 시드 콘텐츠(문구)는 ③의 산출물을 그대로 쓴다 — 부족하면 최소 추가.

검증: uvicorn 띄우고 세션 생성→좋은 답/나쁜 답 시나리오로 응답 제출→리액션과
도입 변주가 실제로 달라지는지 curl 증거. 전체 pytest 통과. 커밋.
```
