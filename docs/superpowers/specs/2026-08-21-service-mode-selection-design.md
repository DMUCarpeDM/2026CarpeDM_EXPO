# 서비스 모드 선택 설계

## 목적

Mirror-Ting의 시작 흐름을 세 가지 독립 서비스 진입점으로 재구성한다.

- 면접: 실전 모의면접
- 직업훈련: 고객응대·현장업무 훈련
- 직장대화: 보고·피드백·협업 대화

세 서비스는 앞으로 각각의 시나리오와 콘텐츠를 확장할 수 있어야 한다. 다만 현재의 카메라·음성 수집, 4-Fit 분석, 세션 API, 리포트는 공통 엔진으로 유지한다.

## 범위

### 포함

- 시작 화면에 세 개의 동등한 서비스 카드로 구성된 모드 선택 UI를 추가한다.
- 선택한 모드의 제목, 설명, 대표 상황, 추천 문구가 이후 설정 및 미리보기 흐름에 반영되도록 한다.
- 모드 정의를 하나의 설정 데이터로 관리해, 새 모드·카피·추천 시나리오를 컴포넌트 복제 없이 추가할 수 있게 한다.
- 기존 디자인 시스템 토큰, 선택 카드, CTA, 반응형 레이아웃을 사용한다.

### 제외

- FastAPI 세션 API와 분석 엔진의 요청·응답 형식 변경
- 4-Fit 점수 계산 및 리포트 데이터 구조 변경
- 모드마다 별도 프론트엔드 컴포넌트나 별도 앱을 만드는 작업
- 기존 시나리오의 백엔드 콘텐츠를 새로 작성하는 작업

## 정보 구조

`home`에서 사용자가 서비스 모드를 선택한 뒤 기존 설정 흐름으로 진입한다.

```text
홈
  → 서비스 모드 선택 (면접 | 직업훈련 | 직장대화)
  → 공통 설정 흐름 (직무 → 시나리오 → 난이도)
  → 공통 미리보기·연습
  → 공통 4-Fit 리포트
```

선택값은 앱의 프론트 상태로 유지한다. `createSession` 호출은 현재와 동일한 payload를 사용한다. 백엔드가 향후 서비스 모드를 명시적으로 지원하면, 서비스 모드 설정 경계에서만 payload 확장을 검토한다.

## UI와 상호작용

- 데스크톱에서는 세 개의 카드가 한 줄(3열)로 배치된다. 모바일에서는 한 열로 쌓인다.
- 각 카드는 아이콘, 서비스명, 한 줄 목표, 대표 연습 상황, `이 모드로 시작하기` CTA를 포함한다.
- 카드 전체가 키보드로 조작 가능하며, focus/hover/selected 상태는 기존 선택 카드 규칙을 따른다.
- 선택 후에는 공통 설정 화면으로 이동한다. 설정 화면의 제목, 설명, 도움말, 비어 있는 시나리오 안내 문구는 현재 서비스 모드의 설정을 사용한다.
- 연습과 리포트에서는 서비스 모드를 보조 맥락으로만 표기한다. 분석 결과·점수 축·API 호출은 바꾸지 않는다.

## 데이터 모델

각 모드에는 최소한 다음 필드를 둔다.

- `id`: 안정적인 식별자
- `label`: UI 표시 이름
- `description`: 서비스 목표
- `icon`: 기존 아이콘 매핑 키
- `accent`: 기존 디자인 토큰 키
- `setupTitle`, `setupDescription`: 공통 설정 화면 카피
- `emptyScenarioMessage`: 해당 모드에 준비된 시나리오가 없을 때의 안내

기존 백엔드 시나리오에는 서비스 모드 필드가 없으므로, 1차 구현에서는 어떤 모드에서도 현재 시나리오 카탈로그를 보여준다. 설정 데이터는 후속 백엔드 필터링을 위한 경계를 제공한다.

## 검증

- 세 모드 카드가 데스크톱과 모바일에서 모두 표시된다.
- 각 카드를 선택하면 공통 설정 흐름으로 이동하고 선택한 모드의 카피가 반영된다.
- 기존 직무·시나리오·난이도 선택과 세션 시작이 유지된다.
- `npm run test`와 `npm run build`가 통과한다.
- 브라우저에서 서비스 선택부터 설정 화면까지 직접 확인한다.
